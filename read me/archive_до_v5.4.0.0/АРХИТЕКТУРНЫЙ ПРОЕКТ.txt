Документ — единственный достоверный источник правды о формате базы и о
логике кнопок сайта на момент сборки v5.2.0.4. Ядро v5.2.0.0/v5.2.0.1/
v5.2.0.3 осталось нетронутым; добавлена новая ЧАСТЬ 0-В ниже с точечной

в столбик при неизменном ряде кнопок звонка/WhatsApp, и полная
перестройка окна «⚠️ Ошибка» (карусель категорий вместо свободного
текста, нативные тайм-пикеры и селектор кодов вахты вместо свободного
текста Графика, авто-префиксы Г6/Г8). ЧАСТЬ 0 и ЧАСТЬ 0-Б ниже —

  0.1 СУВЕРЕННАЯ СТРУКТУРА КАТЕГОРИЙ (ВАРИАНТ Б) — каскад 9×9
  ---------------------------------------------------------------------------
  Каталог категорий (супер-плитки 1-го этажа и под-плитки 2-го этажа —
  эмодзи, двуязычные названия, теги-карусели) БОЛЬШЕ НЕ лежит литералом
  внутри script.js. Он вынесен в отдельный суверенный файл
  categories.json — это КОНТЕНТ-КАТАЛОГ, завязанный на цифровую математику
  масок Г17/Г19, а не «текст интерфейса», поэтому он НЕ внутри
  languages.json (это был рассмотренный вариант А, отклонён в пользу
  отдельного файла — решение утверждено явно).

  Структура categories.json:
    {
      "schemaVersion": "v5.2.0.1",
      "grid": "9x9",
      "superTiles": [ {id,emoji,ru,kz[,hidden]}, ...9 штук ],
      "subTiles": { "1": [ {sub,ru,kz,tags[,hidden]}, ...9 штук ], ..., "9": [...] }
    }
  Сетка расширена с 6×6 до СТРОГО 9×9 = 81 гнездо. Слоты 7–9 на ОБОИХ
  уровнях (и супер-плитки, и под-плитки каждой супер-плитки) — чистый
  резерв под будущее расширение, помечены "hidden":true. Активное
  содержимое слотов 1–6 перенесено БЕЗ ИЗМЕНЕНИЙ 1:1 из прежнего
  script.js.
  Загрузка: script.js поднимает файл один раз через loadCategories()
  (тот же резилиент-паттерн, что у loadConfig()/loadGeo() — любая сетевая
  неудача тихо гасится, белого экрана не бывает) и присваивает результат
  в ТЕ ЖЕ runtime-имена SUPER_TILES/SUB_TILES, поэтому вся нижестоящая
  логика (idTile/idSub, рендер плиток, matchTagIndex, favGroupLabel,
  buildCandidateRow) не потребовала структурных правок — поменялся только
  источник данных. Рендер супер-плиток (renderTiles) и выбор сектора в
  форме Анкеты (openSectorModal) теперь явно пропускают записи с
  hidden:true — до этой версии такого фильтра на уровне супер-плиток не
  было, потому что скрытых супер-плиток ещё не существовало.

  Как следствие расширения сетки, ПРИНУДИТЕЛЬНО расширены диапазоны C/T1
  в маске Г17 и в парсерах:
    - MASK17_RE в script.js:    [1-6] → [1-9] на обоих местах (C и T1)
    - rowValidate() в script.js: ручные проверки диапазона C/T1 — то же
    - validator.js (scanIdRanges, «Живой Карантин»): вёдра супер-плиток
      расширены с {1..6} до {1..9}
  Повторная серверная проверка всех 5 баз сёл под НОВЫМ диапазоном [1-9]
  дала 0 структурных ошибок (существующие данные используют только
  плитки 1-6, регрессии нет).

  ---------------------------------------------------------------------------
  0.2 НОВАЯ КРОСС-ПРОВЕРКА Г1 ↔ ТИП ЗАПИСИ (rowValidate)
  ---------------------------------------------------------------------------
  Прежний rowValidate() проверял только ФОРМУ масок, но никогда не
  сверял числовое значение Г1 с тем, каким типом записи строка себя
  называет. Это была реальная структурная дыра. Теперь:
    - строка опознана как ЖИТЕЛЬ (Г18 активна, ≠ «0») и при этом ID<10000
      → ошибка auditErrResidentIdRange, карантин;
    - строка опознана как БИЗНЕС (Г18=«0») и при этом ID>9999
      → ошибка auditErrBusinessIdRange, карантин.
  Важно различать ДВЕ разные границы, которые НЕ путать:
    10000  — граница ВАЛИДАЦИИ (минимальный допустимый ID жителя);
    10001  — первое НАЗНАЧАЕМОЕ значение для села без единого жителя
             (см. 0.5 — каскад Оперативного рапорта). Житель с ID=10000
             был бы структурно ВАЛИДЕН, просто автоматика никогда не
             предложит это конкретное число первым.

  ---------------------------------------------------------------------------
  0.3 ЗАКРЫТИЕ ВЕХИ ИМЁН: name_synonyms.json
  ---------------------------------------------------------------------------
  Суверенный файл name_synonyms.json (не часть languages.json) — словарь
  народных синонимов/уменьшительных имён, построенный по утверждённой
  методологии «реальное сканирование + честный паритетный добор»:
    1. Две независимые базовые сетки — славянская и казахская.
    2. Реальное сканирование графы Г3 ВСЕХ строк-жителей (ID≥10001) по
       всем 5 базам сёл — пара помечается "confirmed":true, если канон
       ИЛИ любой её синоним реально встретился как отдельный токен ФИО в
       текущих данных.
    3. Пары, не найденные в текущих данных, остаются в словаре с пометкой
       "confirmed":false (честный добор для полноты и паритета — прозрачно
       видно, что это заготовка «на вырост», а не подтверждённый факт).
  Итог сборки v5.2.0.1 (числа — см. поле "stats" внутри файла):
    - всего пар: 119 (славянских 65 / 54.6% · казахских 54 / 45.4% —
      жёсткий пол 45% на оба лагеря выдержан);
    - подтверждено сканом реальных данных: 46 пар; честный добор: 73 пары;
    - покрытие списка жителей (170 реальных записей): 101 житель, 59.4%
      (выше целевого порога ≥50%).
  Формат одной пары: {canon, synonyms:[...], origin:"slavic"|"kazakh",
  confirmed:bool}.
  ФИО жителя (Г3+Г5) РАЗБИРАЕТСЯ НА НЕЗАВИСИМЫЕ ТОКЕНЫ (Фамилия/Имя/
  Отчество — каждое отдельное слово), а не сравнивается целой строкой:
  nameTokensOf(r) → [токен, токен, ...]. Каждый токен расширяется своей
  синонимической группой через nameSynonymGroup(). Это используется в

  ---------------------------------------------------------------------------
  Раньше следующий свободный ID для новой заявки (residentNextId /
  nextFreeIdInBucket) считался только от уже загруженных строк базы
  (S.rows). Если посетитель (или несколько посетителей подряд, пока
  админ ещё не применил предыдущие заявки к базе) отправлял несколько
  НОВЫХ заявок в одну и ту же категорию одна за другой, S.rows между

      тот же бакет супер-плитка/под-плитка (C/T1).

  до применения первого администратором) — честно 10172, третьему —
  10173. Для бизнеса внутри одного сотого бакета папки — ровно так же:
  1503, затем 1504. Применение заявки в реальную базу админом
  (applyQueueItemToDb) по-прежнему имеет свой отдельный, уже
  существовавший раньше, страховочный пересчёт коллизий — он не тронут.

  setupCategoryButton/openSectorModal/openSubModal/setupScheduleGrid/

  r,draft) с сохранением уже введённых значений остальных граф через

ЧАСТЬ 1. ПАСПОРТ 20-ГРАФОВОЙ БАЗЫ (Г1–Г20)
===============================================================================

Каждая строка одной из пяти текстовых баз сёл округа (baza_zko_baiterek_*.txt)
— это РОВНО 20 граф, разделённых последовательностью " | " (пробел, вертикальная
черта, пробел). Между графами — ровно 19 разделителей. Пустая строка между
«сотнями» ID — это визуальный разрыв Z-серилизации, не часть данных.

  Г1  — ID (абсолютный номер записи)
  Г2  — Папка (текстовое название раздела: для бизнеса — живой текст
        супер-плитки, например «Такси и авто»; для жителей — служебное
        слово «ЖИТЕЛИ»)
  Г3  — Главный заголовок (название организации или ФИО жителя)
  Г4  — Коммерция / владелец (ФИО владельца для бизнеса, «.» для жителей)
  Г5  — Жители / примечание (для жителей — примечание/девичья фамилия/
        должность, «.» для бизнеса)
  Г6  — Городской телефон
  Г7  — Сотовый №1
  Г8  — Сотовый №2
  Г9  — Адрес
  Г10 — Поисковые теги-синонимы
  Г11 — Географическая зона («зона <Название села>»)
  Г12 — График работы (текст, либо код SHIFT|... для цикличных смен)
  Г13 — Социальная метка / место работы
  Г14,Г15,Г16 — служебные резервные графы, всегда буква «R» (контрольная
        тройка — наличие любого иного значения = структурная ошибка)
  Г17 — [HOME LOCK] маска бизнеса (см. Часть 1.1)
  Г18 — [RESIDENT LOCK] маска жителя (см. Часть 1.2)
  Г19 — [SEARCH LOCK] маска поиска (см. Часть 1.3)
  Г20 — Маркер модерации (см. Часть 1.4)

  ---------------------------------------------------------------------------
  ОСОБЫЙ ФОКУС: Г1 — СОТЫЕ Z-ID
  ---------------------------------------------------------------------------
  Расположение карточки на сайте НЕ хранится текстом — оно вычисляется чистой
  математикой прямо из числа в Г1:
      супер-плитка 1-го этажа = floor(ID / 1000)
      под-плитка 2-го этажа   = floor(ID / 100) % 10
  Пример: ID 3312 → floor(3312/1000)=3 (Такси и авто) →
          floor(3312/100)%10 = 3 (Ассенизаторы/Септики).
  Диапазоны: 0–999 — системный резерв (экстренные службы 101/102/103/104/112,
  исключаются из обычного списка при загрузке); 1000–9999 — бизнес-сетка
  (с v5.2.0.1: 9 супер-плиток × 9 под-плиток × до 99 записей в «сотне»,
  слоты 7-9 на обоих уровнях — чистый резерв, hidden:true, физически
  недостижимы через интерфейс, пока их не откроют); 10000+ — Жители (вне
  Z-сетки, свой отдельный диапазон, без супер/под-плитки; 10000 — нижняя
  граница валидации, 10001 — первое авто-назначаемое значение, см. ЧАСТЬ 0).
  Автоматика: при отправке новой Анкеты бизнеса ID вычисляется функцией
  nextFreeIdInBucket(mainId,subId) — первый свободный номер внутри «сотни»
  base=mainId*1000+subId*100, перебор +1…+99.

  ---------------------------------------------------------------------------
  ОСОБЫЙ ФОКУС: Г2–Г3 — Z-ТЕКСТ
  ---------------------------------------------------------------------------
  Г2 (Папка) — не служебный код, а живой текст. Для бизнеса это русское
  название супер-плитки (с v5.2.0.1 — из суверенного каталога
  categories.json, поднятого в runtime-переменную SUPER_TILES, см. ЧАСТЬ 0.1;
  раньше, до v5.2.0.1, каталог был литералом прямо в script.js), для жителей —
  фиксированное слово «ЖИТЕЛИ». Г3 (Главный заголовок) — название/ФИО,
  именно по нему строится Z-сортировка внутри «сотни» (alphabetical localeCompare
  по-русски) при сборке файла (jsSerializeRows) и совпадает с заголовком h3
  карточки на экране.

  ---------------------------------------------------------------------------
  ОСОБЫЙ ФОКУС: Г5–Г6 — ОРДЕР ЖИТЕЛЬ/БИЗНЕС
  ---------------------------------------------------------------------------
  Если запись — бизнес: Г4=владелец (или «.»), Г5=«.».
  Если запись — житель: Г4=«.», Г5=примечание/девичья фамилия/должность
  (или «.»). Это зеркальная пара полей — заполняется строго одна из двух,
  никогда обе одновременно. Г6 (Городской телефон) общий для обоих типов
  записей, заполняется либо «.», либо реальным номером.

  ---------------------------------------------------------------------------
  Г17 [HOME LOCK] — маска бизнеса
  ---------------------------------------------------------------------------
  Формат: X/C/T1/T2/G/L/W1/W2/0/0   (10 компонентов, 9 слэшей)
    X  — индекс села (1–5, должен совпадать с индексом файла базы)
    C  — код супер-плитки 1-го этажа, 1–9 (= floor(ID/1000)) — диапазон
         расширен с [1-6] на [1-9] в v5.2.0.1 под каскад 9×9
    T1 — код под-плитки 2-го этажа, 1–9 (= floor(ID/100)%10) — то же
    T2 — номер активного тега карусели синонимов, 0–4 (жёсткий цифровой
         шлюз: 0 = «Все»/нет тега, 1–4 = конкретный тег из SUB_TILES[C][T1].tags)
    G  — код графика: 1=обычный, 2=круглосуточно, 3=по звонку/выезд, 4=сменный
    L  — городской телефон указан (0/1)
    W1 — WhatsApp подтверждён на Сотовом №1 (0/1)
    W2 — WhatsApp подтверждён на Сотовом №2 (0/1)
    0/0 — два хвостовых контрольных нуля (историческое наследие формата,
          зарезервированы, не несут значения)
  У жителей Г17 всегда равна «0» (короткая форма «пусто»).

  ---------------------------------------------------------------------------
  Г18 [RESIDENT] — маска жителя
  ---------------------------------------------------------------------------
  Формат: X/P/L/M1/M2/0/0   (7 компонентов, 6 слэшей)
    X  — индекс села
    P  — буквальная литера «P» (признак «это житель»)
    L  — городской телефон указан (0/1)
    M1 — WhatsApp подтверждён на Сотовом №1 (0/1)
    M2 — WhatsApp подтверждён на Сотовом №2 (0/1)
    0/0 — два хвостовых контрольных нуля
  У бизнеса Г18 всегда равна «0».

  ---------------------------------------------------------------------------
  Г19 [SEARCH LOCK] — маска поиска
  ---------------------------------------------------------------------------
  Формат: X/K1/K2/K3/K4/0/0   (7 компонентов, 6 слэшей)
    X  — индекс села
    K1 — есть хотя бы один сотовый номер (0/1), реальный факт
    K2 — тип записи: 1=бизнес, 2=житель, реальный факт
    K3 — подтверждён WhatsApp хотя бы на одном сотовом (0/1), реальный факт
    K4 — копия активного тега T2 (0–4) из Г17, реальный факт
    0/0 — два хвостовых контрольных нуля
  Заполняется ВСЕГДА (и у бизнеса, и у жителей) — именно по К3/К4 работает
  «глубокий» поиск (searchParts[2]===2 → поиск по всем полям, не только
  заголовку).

  ---------------------------------------------------------------------------
  Г20 — маркер модерации
  ---------------------------------------------------------------------------
  «$»               — карточка промодерирована, видна посетителям.
  «NEW»             — новая заявка, ещё не внесена администратором в базу.
  «ORIGINAL»        — архивная копия строки ДО правки (парная к EDIT).
  «EDIT»            — предлагаемая правка (парная к ORIGINAL, обе строки
                       идут подряд при отправке заявки на исправление).
  «DELETE_1..4»     — заявка на удаление с кодом причины (1=хозяин против,
                       2=выбытие/не проживает, 3=закрылись [только бизнес],
                       4=дубликат).
  «DELETE_<текст>»  — заявка на удаление со свободным текстом причины.
  Все маркеры, кроме «$», — это сигнал «Живому Карантину»: такие строки
  скрыты от обычных посетителей и попадают в список администратора
  (quarantineMonitor) до тех пор, пока он не внесёт правку руками и не
  заменит маркер на «$».

2.1. РЯД №1 СВЯЗИ (синяя «Позвонить» + зелёные WhatsApp)
-------------------------------------------------------------------------------
Строится функцией phoneBlockHtml(r) для каждой карточки индивидуально —
никогда не рисует пустых кнопок.
  • Собирается список реально заполненных номеров (Городской/Сотовый №1/
    Сотовый №2), в этом порядке.
  • Если номер РОВНО ОДИН — синяя кнопка «Позвонить» это прямая ссылка
    tel:, звонит мгновенно, без модалки (вариант Г наряда).
  • Если номеров ДВА или ТРИ — синяя кнопка открывает модалку выбора
    (openCallPicker), с тем набором пунктов, что реально есть у карточки:
      А) Городской / Сотовый №1 / Сотовый №2 — все три заполнены
      Б) Городской / Сотовый — городской + один мобильный
      Д) Сотовый №1 / Сотовый №2 — оба мобильных без городского
  • Зелёные кнопки WhatsApp показываются СТРОГО по месту: только для
    того сотового номера, у которого реально поднят флаг подтверждения
    (W1/W2 из Г17 для бизнеса, M1/M2 из Г18 для жителей). Городской номер
    WhatsApp никогда не получает. Если подтверждённый WhatsApp-номер
    ровно один — подпись простая «WhatsApp»; если их два — «WhatsApp 1»/
    «WhatsApp 2».

2.2. РЯД №2 ПОДВАЛА УТИЛИТ
-------------------------------------------------------------------------------
Ровно три кнопки на всю карточку, в порядке «Скопировать» → «⚠️ Ошибка»
(строго по центру ряда) → «Поделиться».
  • «Скопировать» — копирует в буфер обмена все реальные номера карточки
    через запятую.
  • «⚠️ Ошибка» — открывает openErrorEditor(r): форму исправления 12 полей
    карточки (без системных граф/ID), с итоговой двойной отправкой
    ORIGINAL+EDIT в очередь модерации, либо переход в openDeleteReasonModal
    («🗑️ Удалить анкету») для заявки на удаление.
  • «Поделиться» — системный Web Share API (navigator.share), либо запасной
    вариант — копирование текста в буфер, если Share недоступен в браузере.
    С v5.2.0.1 текст — трёхэтажная визитка businessCardText() строго по
    графам Конституции (бренд/название/владелец-примечание/теги/телефон
    и, если заполнены оба поля config.json, необязательная 6-я строка-
    реклама приложения), см. ЧАСТЬ 0.4. Никакого графического QR в этой
    кнопке нет и не было — только текст.

2.3. ПРАВАЯ ИЗОЛИРОВАННАЯ БУЛАВКА (📌)
-------------------------------------------------------------------------------
Полностью независима от звезды Избранного — отдельное состояние
S.pinned/S.pinnedOrder, отдельные функции togglePin/savePinned/loadPinned.
Тап по булавке фиксирует карточку строго в ТОП любого текущего списка —
выше алфавитного радара и выше любой другой сортировки вида (применяется
функцией applyPinnedOnTop() в самом конце конвейера рендера, после всех
остальных сортировок). Самая недавно закреплённая карточка встаёт первой
среди закреплённых. Работает одинаково в любой вкладке (Жители/Поиск/
Избранное/Категория).

2.4. ЗВЕЗДА ИЗБРАННОГО (⭐)
-------------------------------------------------------------------------------
Отдельное состояние S.favorites/S.favOrder, отдельные функции toggleFav/
saveFav/loadFav — ничего общего с булавкой. Добавляет/убирает карточку из
персонального списка «Избранное», который открывается через нижнюю
навигацию.

2.5. ШЕСТЕРЁНКА НАСТРОЕК ИЗБРАННОГО (⚙️, дефолт «По категориям»)
-------------------------------------------------------------------------------
Иконка в правом верхнем углу заголовка вкладки «Избранное». Открывает
favSettingsModal() с четырьмя взаимоисключающими режимами:
  • «По алфавиту (А-Я)»       — строго по алфавиту заголовка.
  • «По категориям» (ЖЁСТКИЙ ДЕФОЛТ при первом запуске, принудительно
    записывается в хранилище при первом вызове loadFavSettings(), если
    ключа ещё не существует) — группировка по горизонтальному Z-порядку
    супер-/под-плиток (Магазины→Мастера→Такси→Медицина→Госсектор→Прочее),
    жители — отдельная группа в конце.
  • «По времени добавления»   — в порядке, в каком карточки были добавлены
    в Избранное (S.favOrder).
  • «Ручной режим»             — свободная Drag-and-Drop пересортировка
    (Pointer Events, не нативный HTML5 draggable — надёжнее на сенсорных
    телефонах), порядок хранится в S.favManualOrder.
  Отдельный чекбокс «Показывать VIP-рекомендации» добавляет блок «👑
  VIP-рекомендации» внизу списка (карточки с активной записью в
  reklama.txt, не входящие в Избранное). Булавка работает поверх любого
  режима — закреплённые карточки всегда отдельной лентой «📌 Закреплено»
  сверху, независимо от выбранной сортировки.

2.6. ОЧЕРЕДЬ ЗАЯВОК (Админ-пульт → 🛡️)
-------------------------------------------------------------------------------
Показывает ОБЪЕДИНЁННЫЙ список заявок: удалённые (из requests.txt через
GitHub API) + локальные (localStorage, не успевшие синхронизироваться).
Под КАЖДОЙ заявкой — независимый ряд из трёх кнопок:
  • «Внести в базу» — применяет applyQueueItemToDb: безопасно вставляет уже
    готовую 20-графовую строку (ID/маски посчитаны автоматически ещё на
    этапе отправки Анкеты) в нужный файл базы, разрешает конфликт ID внутри
    той же «сотни» при необходимости, меняет маркер на «$», коммитит
    через GitHub API, пересобирает файл по Z-правилам (jsSerializeRows).
  • «📋 Копировать» — копирует в буфер именно строку ЭТОЙ заявки.
  • «🗑️ Отклонить» — снимает заявку из очереди без внесения в базу.

2.7. ДВУХСЛОЙНЫЙ ГИБРИДНЫЙ ПОИСК
-------------------------------------------------------------------------------
Работает для ЛЮБОЙ буквы алфавитного радара без исключений, двумя
независимыми слоями:
  ЭТАП 1 (текстовый поиск) — ввод 2+ символов в строку поиска даёт список
    результатов по всей текущей базе (searchBaseRows/residentBaseRows).
  ЭТАП 2 (наложение буквы) — не очищая текст, тап по активной букве радара
    жёстко фильтрует ТЕКУЩИЙ список по первой букве заголовка
    (applyAlphabet).
  ЭТАП 3 (повторный тап = сброс) — повторный тап по уже активной букве
    гасит фильтр буквы и возвращает список к состоянию ЭТАПА 1.
  ЭТАП 4 (обратный шлюз) — если буква радара активна, а поле поиска пустое,
    режим алфавитного радара сохраняется; как только посетитель набирает
    РОВНО 2 живые буквы в поле поиска, activeLetter автоматически гаснет и
    результаты переключаются на поиск по строке (реализовано флагом
    wasEmpty в обработчике debounce/Enter поля поиска).
  Доступность букв радара считается ДИНАМИЧЕСКИ по текущему реальному
  рабочему набору данных (searchAlphabetSourceRows) — коммерция и жители
  объединённо во вкладке «Поиск», только жители во вкладке «Жители».

     завязанные индексами на маски Г17/Г19), а не «текстом интерфейса».
  2. Беспилотный гостевой шлюз Анкеты добавления: готовая 20-графовая
     строка (с маркером «$») автоматически и скрытно отправляется в
     изолированный GitHub Issues текущего репозитория (owner/repo —
     динамически из location.hostname вида owner.github.io, с
     переопределением в config.json → repositoryOwner/repositoryName).
     Требует одноразовой настройки Владимиром узко-ограниченного токена
     config.json → guestIssuesToken (только «Issues: Read and write» на
     этот репозиторий). Пустой токен = безопасный no-op, обычная очередь
     модерации продолжает работать без изменений.
  3. Фоновый робот-радар в service-worker.js: Periodic Background Sync
     (при поддержке браузера/Android — честно оговорённое ограничение
     платформы, не гарантирует точный интервал) раз в ~30 минут проверяет
     GitHub Issues/базы на новые заявки, дубликаты ID и немодерированные
     маркеры, выводит системную плашку Android. Тап по плашке открывает
     Админ-пульт (без обхода секретного SHA-256 кода — только если токен
     администратора уже персистентно сохранён на этом устройстве).
  4. Два ранее «мёртвых» инструмента (passportModal, auditModal) подключены
     к Админ-пульту кнопками 🧪/📊.

ЧАСТЬ 4. ЧЕСТНЫЕ ОГОВОРКИ (платформенные ограничения)
===============================================================================
  • Periodic Background Sync не гарантирует точные 30 минут — это зависит
    от вовлечённости пользователя и эвристик браузера, недоступен в iOS
    Safari и в обычной (не установленной) вкладке.
  • Service Worker физически не может прочитать localStorage — токен
    администратора передаётся в него только через postMessage со страницы
    и живёт у него в памяти до перезапуска воркера. Чтобы фоновый радар
    переживал перезапуски между сеансами, администратор может отдельно
    (явным действием в Админ-пульте) сохранить токен персистентно на своём
    устройстве — это сознательно отдельная, более широкая по сроку жизни
    настройка, отличная от обычного сессионного токена.

   кэшируется в localStorage (cart_plat_stats) на 4 часа. IP и личные данные не собираются.
   Сервер (google_apps_script_webhook.gs): листы Stats_Devices (по строке на устройство)

   сутки и месяц по Asia/Oral. Сводка кэшируется на сервере на 5 минут.
   ВАЖНО: скрипт нужно ПЕРЕРАЗВЕРНУТЬ («Управление развёртываниями» → новая версия),
