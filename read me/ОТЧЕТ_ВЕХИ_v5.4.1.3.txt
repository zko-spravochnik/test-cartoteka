КАРТОТЕКА — ОТЧЁТ ВЕХИ v5.4.1.3 (2026-10-30): БРОНЯ ОЧЕРЕДИ ЗАЯВОК И МОСТА GITHUB

1. КОМПЛЕКТ ИЗ 6 КНОПОК (всегда на месте, сетка 2 на 3; недоступные по статусу серые)
[ Одобрить ] (активна у «Новой») · [ Редактировать ] · [ В файл + Буфер ] и [ В GitHub ] (активны у «Одобренной», кроме DELETE) · [ Внесена ] · [ Отклонить ].
Отдельной кнопки «Копировать» больше нет. Все кнопки изменений требуют Мастер-пароль.

2. РЕДАКТОР ОПЕЧАТОК
«Редактировать» (или тап по серому окошку строки, затем «Редактировать») превращает 20 граф в поля ввода. «Применить» проверяет: нет лишней черты «|», строка проходит валидатор
базы, у EDIT нельзя менять ID, у NEW новый ID не должен быть занят. Исправленная строка хранится на телефоне в памяти вкладки (пометка ✎) и дальше используется ВСЕМИ кнопками
вместо сырого текста. Если заявка уже в облаке, шлюз получает действие updateRow и обновляет строку в таблице синхронно.

3. [ В ФАЙЛ + БУФЕР ]
В одном клике: сначала navigator.clipboard.writeText (пока действует касание), одновременно сервер на телефоне дописывает строку в файл села (копия файла в backups_local, проверка дубля).
Для EDIT вместо дописывания идёт замена. Результат показывается двумя отметками: 📄 файл и 📋 буфер.

4. [ В GITHUB ] БЕЗ УЧАСТИЯ ХРОМА
Сервер (cartoteka_server.py, /__github_push) берёт токен GitHub из оперативной памяти, читает файл села через API (содержимое и sha), применяет правку, отправляет обновлённый файл (PUT с sha) и
получает ответ 200/201 с хешем коммита. При конфликте 409 перечитывает и повторяет до 3 раз. Затем обновляет счётчики села в конфиге репозитория (сбой не отменяет коммит) и сам шлёт в Telegram
рапорт синхронизации (репозиторий, село, действие и ID, короткий хеш коммита, время) по токену и ID бота из оперативной памяти. Страница показывает «GitHub ✔» и «Telegram ✔/✖» отдельно.
Ошибки по-русски: токен не принят, нет права записи, репозиторий не найден, конфликт, нет связи.

5. ПРАВКА СТРОКИ ПО ID С ПРОВЕРКОЙ ИНДЕКСОВ (EDIT)
Старая строка ищется в базе по уникальному ID. Отказ: ID не найден; несколько строк с этим ID; старая строка в файле не совпадает с оригиналом заявки; не совпали индексы (графы R | R | R и индекс
села X в масках Г17–Г19). Идентичная строка уже в файле считается «уже внесена». «Отклонить» убирает заявку из очереди (в облаке статус «Отклонена»), оригинал в справочнике не трогается.
DELETE по-прежнему вносится вручную (серые кнопки записи).

6. ПАМЯТЬ СЕРВЕРА
Все строки secrets.txt после кнопки «Считать все коды из файла» лежат ТОЛЬКО в оперативной памяти сервера (SECRETS_MEM); новых файлов с секретами нет, выключили сервер, память очищена.
Как и раньше, открытые значения (ссылки, имя репозитория, ветка) записываются в config.json и test_config.json; токены и пароли туда не попадают.

7. РАДАР ПРАВОК
В режиме EDIT верхний блок (оригинал): изменённые графы мягко-красные, зачёркнутые; нижний блок (новые данные): изменённые графы сочно-зелёные, жирные; совпавшие графы белые.
Графы сравниваются попарно по номеру; счётчик «изменено граф: N». Подсветка пересчитывается при вводе в редакторе.

8. ШЛЮЗ (google_apps_script_webhook.gs v5.4.1.3)
Новое действие updateRow (ADMIN_CODE + MASTER_CODE): обновляет строку заявки в таблице. После обновления файла: кремовая кнопка в пульте, затем НОВАЯ версия развёртывания.

9. КЭШ PWA
Кэш cartoteka-v5.4.1.3 / test-cartoteka-v5.4.1.3, манифест 5.4.1.3, dbEpoch новый, updateCritical = true.

10. ПРОВЕРКА
Проверено в среде разработки на имитации GitHub и Telegram: NEW, дубль, EDIT с конфликтом 409 и повтором, отказы по индексам, ID, оригиналу, DELETE, замена в локальном файле, блокировка без сессии;
шлюз updateRow на имитации таблицы; интерфейс очереди (6 кнопок, радар, редактор, запрет смены ID). НЕ проверено вживую: настоящий GitHub, Telegram, Google. Эту проверку выполняет администратор.
